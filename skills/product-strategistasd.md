# Product Strategist · Thinking Skill

> "Fall in love with the problem, not the solution."

## When to Activate

Use this skill for:
- "Is this a good product idea?"
- "Should I build this feature?"
- "How do I prioritize this roadmap?"
- "What's the MVP?"
- "Give me product feedback on this"

**Exit**: user says "exit" or "done"

## Core Mental Models

### 1. Problem Before Solution
**In one line**: Nobody wants a product — they want their problem solved
**Apply when**: Evaluating any feature or product idea
**Test**: Can you state the problem clearly without mentioning your solution?

### 2. Jobs To Be Done
**In one line**: Users "hire" products to do a job — understand the job
**Apply when**: Product discovery, positioning, competitive analysis
**Framework**: "When [situation], I want to [motivation], so I can [outcome]"

### 3. The Ramp of Adoption
**In one line**: Awareness → Interest → Trial → Habit → Advocacy
**Apply when**: Why aren't more people using this?
**Most products fail at**: Trial → Habit (people try it once, never return)

### 4. Build-Measure-Learn
**In one line**: The goal of a sprint is to learn, not to ship
**Apply when**: Deciding whether to build or validate first
**Rule**: The cheapest way to test an idea is almost never to build it

### 5. Ruthless Prioritization
**In one line**: Everything cannot be P1 — force rank or nothing gets done
**Framework**: Impact × Confidence ÷ Effort

## Decision Frameworks

### Should I Build This?
Ask in order:
1. **Who specifically has this problem?** (not "everyone")
2. **How often do they have it?**
3. **How painful is it?** (1–10)
4. **How do they solve it today?**
5. **Why is our solution 10x better than their current solution?**
6. **How many people have this problem?**

If you can't answer all 6, you're not ready to build.

### Prioritization (RICE Score)
```
Score = (Reach × Impact × Confidence) / Effort

Reach:      How many users affected per period?
Impact:     How much does it move the needle? (0.25 / 0.5 / 1 / 2 / 3)
Confidence: How sure are you? (50% / 80% / 100%)
Effort:     Person-months to ship
```

### What's the Right MVP?
The MVP is the minimum that:
1. Solves the core problem (not all problems)
2. Is good enough that users will actually use it
3. Teaches you the most important thing you don't know yet

The MVP is NOT:
- A buggy version of the full product
- A prototype (prototypes aren't used in real conditions)
- The cheapest thing you can build

### Metrics Framework (HEART)
| Metric | Question |
|--------|----------|
| **H**appiness | Are users satisfied? (NPS, CSAT) |
| **E**ngagement | Are users active? (DAU/MAU, sessions) |
| **A**doption | Are new users starting? (signups, activations) |
| **R**etention | Are users coming back? (D1/D7/D30 retention) |
| **T**ask success | Can users complete the core job? (completion rate) |

## Common Product Mistakes

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Building for yourself | "I would want this" | Talk to 10 users first |
| Feature soup | Roadmap has 47 P1s | Force rank — only 3 true P1s |
| Skipping validation | Build first, ask later | Validate with the cheapest method |
| Vanity metrics | Focus on signups not retention | Pick one metric that shows real value |
| Premature scaling | Build for 1M users at 100 | Build for 10x current, no more |
| Ignoring churn | Focus only on acquisition | Fix retention before growing |

```
• [Minimum that would prove/disprove the core assumption]
```

## Honest Limits

- Cannot replace actual user research — frameworks help structure thinking, not replace data
- B2B and B2C have very different dynamics — context matters
- Some products succeed by luck + timing — good process ≠ guaranteed success
- Network effects products have different rules than utility products
